Jira webhooks in Astra

How a comment on a Jira issue becomes an agent turn — and the eleven places where that path deliberately, or accidentally, stops.

TL;DR

Astra can now be summoned from a Jira issue. You write bwai: draft the release notes as a comment; Jira Data Center posts the event to POST /api/webhooks/jira; the API finds the agents that declare the jira-comment trigger, opens (or reuses) a session bound to that issue key, and runs one agent turn. The whole comment thread on an issue is one conversation.

The interesting part is not the happy path — it is how many gates the request passes through, and that the endpoint tells you which gate stopped it. Unlike the older GitLab webhook, which answers 202 before deciding anything, the Jira endpoint decides synchronously and returns a real status: 404 when no agent claims the trigger, 409 when a turn is already running on that issue, 200 ignored when nobody typed a keyword.

  • What — one endpoint, comment events only, fanning out to every environment-matched agent runtime.
  • Why — let a human trigger an agent from where the work is discussed, without leaving Jira.
  • How — synchronous admission (parse → filter → keyword → session → lock), then the agent turn deferred to a FastAPI background task.
  • Watch out — the endpoint is unauthenticated, the reply-loop guard is content-based, and the busy lock lives in one process's memory.

Background: what Astra already had

New to Astra? Start here (skip if you know the three apps)

Astra runs Claude Code in the cloud. Three apps: web (React chat UI), api (FastAPI — sessions, auth, proxying to the runtime), and core (an AWS Bedrock AgentCore runtime that actually executes Claude Code). Each configured agent is deployed as one ARM64 runtime per environment, so the same agent release may exist as dev-release and uat-release. Agents are declared in agents/agents.yaml; the API discovers their live runtimes from AWS and caches them for five minutes.

A session is a conversation with an agent. Sessions can carry a ref — a namespaced external key. That is the trick that makes webhooks conversational: look up the session by ref, and the second event continues the first event's thread instead of starting over.

Before this change, one webhook already existed: GitLab. It set the shape that Jira inherits — a ref-keyed session, a triggers list in agents.yaml, fan-out to every discovered runtime, and an in-process lock so one session never runs two turns at once.

It also set a shape worth not inheriting. The GitLab endpoint returns 202 immediately and then decides in the background. If the session was busy, or the deployment is in local mode, or no agent matched, GitLab is told "accepted" and the outcome is only a log line. Fine when a human is watching CI; useless when a human is waiting on a Jira ticket.

So the change refactored the shared half out of the GitLab module into two new files — runner.py (session resolution, lock, dispatch) and env_binding.py (which runtimes may answer) — and gave Jira a second admission model on top of them.

Definition — admission. Everything that happens before the agent turn: resolve the session, title it, check the deployment can run agents, take the lock, render the prompt. GitLab does this after replying (async-202). Jira does it before (synchronous), and only defers the turn itself. runner.py says plainly that the synchronous pair is the model to prefer for new providers.

Intuition: a gauntlet of gates

Think of the endpoint as a corridor of doors. A comment must open every one. Each door has a name, and that name is what comes back in the response body — which is why debugging a silent agent is a matter of reading one JSON field.

Toy example: one comment, two runtimes

Suppose release is deployed twice — dev-release and uat-release — and neither sets same_runtime_env_bound. Someone comments on BWATDFNG-58579:

{
  "webhookEvent": "comment_created",
  "issue":   { "key": "BWATDFNG-58579",
               "fields": { "summary": "Webhook for Jira comments" } },
  "comment": { "id": "884211",
               "author": { "name": "ihor_penskyy" },
               "body": "bwai: draft the release notes" }
}

Both runtimes pass the env filter. Both match the keyword. dev-release is idle, so it takes the lock; uat-release happens to already be running a turn on the same issue. The response is partial, and says so:

202 Accepted
{ "status": "accepted",
  "dispatched": ["dev-release"],
  "skipped": { "uat-release": "busy" } }

If no runtime had been admitted, there would be no single reason to report — so the module keeps one ordered table and picks the most severe: a broken session (500) outranks a misconfigured deployment (503 local mode), which outranks a turn merely already running (409).

Edge case worth internalising. env_not_bound is a 200, not an error. When an agent opts into same_runtime_env_bound, exactly one deployment answers and every other deployment is supposed to shrug. Treating that as a failure would make every non-owning environment log noise for every comment.

The reply loop, and the thin thread holding it shut

Here is the sharpest idea in the change. The agent answers by posting a comment on the issue. That comment fires the webhook again. Nothing structural distinguishes the agent's comment from a human's — Jira does not mark it as bot-authored in a way the endpoint checks.

What breaks the loop is content: the agent's own comment contains no invocation keyword, so it invokes nothing. The guard is a convention the agent must keep, not an invariant the code enforces.

Because the protection is content-based and therefore fragile, the config loader defends what it can at startup: an agent with the jira-comment trigger must set direct_invocations_only: true, and that in turn must have a non-empty invocation_keywords. load_agents raises rather than boot a config that would remove the guard.

The lock-ownership dance in _admit_all and _queue_admitted

Fan-out makes lock handling genuinely tricky, because admission takes locks one runtime at a time and the request can still fail afterwards. Two except blocks cover it, and both release every lock taken so far:

# jira.py — admitting runtime N raises after 1..N-1 took locks
try:
    for agent in agents:
        outcome = await admit_agent_event(...)
        ...
except Exception:
    for event in admitted:
        await release_admitted_event(event)
    raise
# jira.py — if queueing fails, FastAPI runs NO background task,
# so even already-queued events must be released here
try:
    for event in admitted:
        background_tasks.add_task(dispatch_admitted_event, event)
except Exception:
    for event in admitted:
        await release_admitted_event(event)
    raise

Both matter because session locks have no TTL. A missed release does not heal; it holds that session until the process restarts.

Keyword matching, and why subwai: does not match bwai: 
alternatives = "|".join(re.escape(k) for k in cfg.invocation_keywords)
return bool(re.search(rf"(?<!\w)({alternatives})", comment_body, re.IGNORECASE))

The negative lookbehind requires the keyword to start a word. Case-insensitive, keywords are regex-escaped, and there is no trailing boundary — so bwai: matches anywhere a word begins, including mid-sentence and inside quoted text.

Note the fail-closed branch: if direct_invocations_only is true but invocation_keywords is empty, the function returns False rather than matching everything. Startup validation should make this unreachable; the code refuses to rely on that.

Prompt shape, and what is deliberately left out

_build_comment_prompt renders a flat, YAML-ish block: session id, event type, a fixed allowlist of issue fields (summary, issuetype, status, priority, parent, fixVersions, components, labels, assignee/reporter emails), then comment id, author, and the two free-text blocks — description and comment body.

A full Jira issue payload carries every custom field and would dominate the agent's context. An agent that needs more reads the issue through the Jira API using issue.key. Note also the logging discipline: on a no_mention skip the code logs the issue key, comment id, and author — never the body, because Jira comments routinely carry customer data.

Current restrictions

Some of these are design decisions with a stated rationale; others are the edges the first version simply has not reached yet. Worth separating the two.

Deliberate scope

RestrictionConsequence
Comment creation onlyComment edits and deletions, issue creation, field changes, and status transitions all return 200 ignored / event_not_handled. Editing a comment to add bwai: does nothing.
Jira Data Center onlyThe author is read as comment.author.name, falling back to .key, then the top-level acting user.name. Jira Cloud identifies users by accountId, so a Cloud payload yields an empty author.
Fixed field allowlist in the promptNo custom fields, no attachments, no prior comments. The agent sees this comment plus the issue header, and must call the Jira API for anything else.
Direct invocation is mandatoryAn agent cannot be configured to answer every comment on an issue — startup validation forbids it, because that is the reply loop.
One turn per issue per agentA second comment while a turn is running gets 409 busy. It is dropped, not queued, so the follow-up instruction is lost.

Sharper edges

1. The endpoint is unauthenticated. No shared secret, no signature check, no JWT. _triggered_agents notes it explicitly: "Webhook auth is via the endpoint URL, not JWT, so allowed_roles is bypassed here." The API README says to restrict access at the network level. So the URL is the credential, and allowed_roles — the mechanism that keeps release to the dev role in the UI — does not apply on this path.
2. Anyone who can comment can invoke the agent. There is no author allowlist and no human check. A Jira automation rule, an integration bot, or any user with comment permission on the issue can start an agent turn that runs with the agent's own credentials.
3. The loop guard is a convention. Nothing stops the agent from quoting a keyword back — "you asked: bwai: cut a release" re-invokes it, and the reply is itself a comment. Both the module docstring and the README state the rule in bold; only the config-level part of it is machine-checked.
4. No idempotency. comment.id reaches the prompt but is never used for deduplication. A Jira retry, or a manual redelivery of the same event, runs the turn a second time.
5. Delivery is best-effort, in-process. The turn runs as a FastAPI BackgroundTask in the API pod. A restart or deploy between the 202 and the turn silently loses it. There is no queue, no retry, and no dead-letter path.
6. The busy lock is per-process. try_acquire_session_run is an in-memory set guarded by an asyncio.Lock. Today the Helm chart runs replicaCount: 1, so the guard holds — but it is a scaling constraint, not a distributed lock. Two replicas would let two turns run on one session.
7. Failures after the 202 are invisible in Jira. If the agent turn throws, record_webhook_error writes it to the session's error_message. The commenter sees no reply and no explanation — they must open Astra to find out why.
8. Fan-out is the default, and duplicates are opt-out. release in agents.yaml does not set same_runtime_env_bound, so every discovered runtime for the slug is invoked. If both dev-release and uat-release are live, one comment gets two agents working on the same issue. That is also true in reverse: the flag is the fix, and it must be set per agent.
9. Runtime discovery is cached for five minutes. A freshly deployed runtime may not answer comments yet, and 404 no_trigger_agent can mean "discovery has not caught up" rather than "misconfigured".
10. Local development cannot exercise the turn. Without AgentCore the admission stage rejects with 503 unavailable. The gates are testable locally; the agent turn is not.
