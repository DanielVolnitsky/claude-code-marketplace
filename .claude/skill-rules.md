# Skill Quality Reference

## Critical

**Must Fix.** Will definitely lead to significant issues if left as is (e.g. broken skill discovery, silent runtime failures, security exposure).

| # | Rule | Why It Matters | Bad → Good |
| --- | --- | --- | --- |
| C1 | Description written in first or second person ("I can help you…", "You can use this to…") | The description is injected directly into the system prompt. Inconsistent point-of-view causes skill discovery failures — Claude may not trigger the skill when it should. | _Bad:_ "I can help you process PDFs" · _Good:_ "Processes PDF files and extracts text" |
| C2 | Description missing explicit when-to-use triggers | Claude selects skills from 100+ candidates using the description as the primary signal. Without clear trigger phrases, the skill will not activate reliably. | _Bad:_ "Processes documents" · _Good:_ "Processes PDF files. Use when the user mentions PDFs, forms, or document extraction." |
| C3 | Deeply nested file references (SKILL.md → A.md → B.md) | Claude may read only partial content of second-level references (e.g. `head -100`), silently missing critical instructions. All linked files must be reachable in one hop from SKILL.md. | Keep all reference files one level deep from SKILL.md |
| C4 | Hardcoded secrets, tokens, or credentials in skill content | Skills are version-controlled and loaded into agent context. Any secret becomes an immediate exposure risk across every session that loads the skill. | Reference environment variables by name; document required env vars in the skill |
| C5 | MCP tool references not using fully qualified `ServerName:tool_name` format | When multiple MCP servers are available, unqualified tool names cause "tool not found" errors at runtime — the skill silently fails with no clear error path. | _Bad:_ `bigquery_schema` · _Good:_ `BigQuery:bigquery_schema` |
| C6 | Skill fetches content from external URLs without justifying the source as safe and necessary | External content is injected directly into the agent's context. Even trustworthy sources can be compromised over time, turning a well-intentioned skill into a prompt injection vector. Requirement: external URL fetching must be justified and verified not to contain malicious instructions. | _Bad:_ "Fetch the latest schema from https://example.com/schema.json" · _Good:_ Embed the schema directly in the skill, or explicitly document why the URL is trusted and how it is monitored for changes |
| C7 | Skill directs Claude to perform operations outside its stated purpose (unexpected network calls, file access, or data transmission to external systems) | Skills with access to sensitive data can silently leak it if they instruct Claude to make unjustified external calls or access unrelated files. Violates the principle of least privilege and the security requirement that skills must not expose data to external systems. | Audit every network call and file access instruction in the skill; remove or explicitly justify any operation not required by the skill's stated purpose |
| C8 | Windows-style backslash paths in file references | Backslash paths fail silently on Unix/macOS environments — the majority of Claude Code users. A skill with broken paths fails every time it is invoked on those systems. | _Bad:_ `scripts\helper.py` · _Good:_ `scripts/helper.py` |
| C9 | Script execute-vs-read intent not made explicit | Ambiguous intent causes Claude to either run a script that was meant as reference material, or to read a script that was meant to be executed — both produce wrong behavior with no visible error signal. When Claude reads a script instead of executing it, the full script content is also loaded into context, bloating it with content that serves no purpose. | _Bad:_ "See `analyze_form.py`" (ambiguous) · _Good:_ "Run `analyze_form.py` to extract fields" (execute) vs. "Read `analyze_form.py` for the extraction algorithm" (reference) |
| C10 | Missing validate-and-retry loops for quality-critical or destructive tasks | Multi-step workflows without explicit validation steps allow silent failures to propagate. Claude will proceed through subsequent steps even when an intermediate output is wrong. | Add "validate → fix → re-validate" steps before any irreversible operation |

## Important

**Should Fix.** May not cause immediate failures, but is serious technical debt or degrades reliability/context efficiency.

| # | Rule | Why It Matters | Bad → Good |
| --- | --- | --- | --- |
| I1 | Description vague or missing domain-specific key terms | Claude uses keyword matching in the description for skill selection. Generic descriptions reduce trigger accuracy, causing missed activations in the scenarios the skill was built for. | _Bad:_ "Helps with documents" · _Good:_ "Extracts text, tables, and form fields from PDF documents" |
| I2 | Skill exists to paper over a broken process | Skills encode the correct way to do things, not workarounds for broken tooling. A skill that codifies a workaround accumulates silent technical debt and makes the underlying problem harder to find and fix. Such skills must not appear in the marketplace. | Determine whether the real fix is a process, config, or documentation change |
| I3 | Time-sensitive information without a versioning wrapper | Date-conditional instructions ("if before August 2025…") become silently wrong as time passes, permanently degrading the skill's guidance without any visible error. | Wrap deprecated approaches in a collapsed "Old patterns" `<details>` section; keep the main body current-only |
| I4 | Multiple approaches offered without a clear default | Presenting 3+ equivalent options forces Claude to choose ad hoc, producing inconsistent results across sessions. Skills should prescribe a path; alternatives are for documented edge cases only. | Pick a default; document alternatives as explicit escape hatches with clear activation conditions |
| I5 | Scripts crash on edge cases instead of handling them explicitly | Scripts that fail with unhandled exceptions force Claude to improvise recovery, leading to inconsistent behavior. Expected error conditions should be caught with explicit fallback logic and informative messages. | Use try/except blocks with specific handlers; provide fallback behavior or clear error messages pointing to the root cause |
| I6 | Script dependencies not listed with explicit install instructions | Skills that silently assume packages are available will fail in new or clean environments with cryptic import errors. Required packages must be declared with explicit install commands. | _Bad:_ "Use pdfplumber to process the file" · _Good:_ "Install: `pip install pdfplumber`, then use…" |
| I7 | Skill packages a one-time action that will not be repeated across sessions | Skills are for knowledge applied repeatedly across many sessions — that is the bar for what belongs in the skill library. A task that will only ever run once is not a skill; it is a prompt. Packaging it as a skill misuses the mechanism: the skill will never activate meaningfully again, it lowers the quality bar for the library, and it pollutes discovery for every future session. If the guidance is not reusable, it does not belong here. | Use a direct prompt for one-time tasks; convert to a skill only when the same guidance will be needed across multiple future sessions |
| I8 | SKILL.md body exceeds 500 lines without progressive disclosure | Exceeding 500 lines degrades performance and bloats context on every invocation. Content must be split into linked reference files. | Move large content into `reference/` subdirectory files linked from SKILL.md |
| I9 | Instruction specificity not matched to the task's fragility | The right level of instruction freedom depends on the task. Step-by-step recipes are correct for fragile, error-prone operations where exactly one safe path exists. High-level direction is correct for tasks where context determines the best approach and multiple valid paths lead to success. Mismatching the two — over-prescribing flexible tasks or under-specifying fragile ones — produces either unnecessarily rigid behavior or inconsistent results. | _Low freedom (fragile/critical):_ "Run exactly: `python scripts/migrate.py --verify --backup`. Do not modify the command or add flags." · _High freedom (context-dependent):_ "Review code structure, check for edge cases, suggest readability improvements, verify project conventions." |
| I10 | Inconsistent terminology within the skill | Mixing "API endpoint" / "URL" / "route" or "field" / "box" / "element" forces Claude to infer equivalence, increasing risk of misapplication when context shifts mid-workflow. | Pick one term per concept and use it throughout; define aliases explicitly if external systems use different names |
| I11 | Reference files longer than 100 lines missing a table of contents | Claude may preview large files with partial reads. A table of contents at the top ensures it sees the full scope of available information even from a partial read, allowing it to jump to relevant sections. | Add a `## Contents` section at the top of any reference file over 100 lines |
| I12 | No copyable checklist for complex multi-step workflows (4+ steps) | Checklists that Claude can copy and track prevent step-skipping in long workflows and surface progress to the human partner. Without them, Claude may skip validation steps under time pressure. | Add a copyable markdown checklist for any workflow with four or more steps (e.g. a `## PDF form filling workflow` section with `- [ ] Step 1…` task items to check off). |

## Minor

**Nice to Have.** Will not cause issues; makes the skill objectively better and easier to maintain.

| # | Rule | Why It Matters | Recommendation |
| --- | --- | --- | --- |
| M1 | Skill name not in gerund form | Gerund names ("Processing PDFs", "Analyzing Data") clearly describe the activity and improve searchability and readability in the skill library. Consistent naming also makes skills easier to reference in documentation. | Prefer gerund: _df-processing-pdfs_ over _df-pdf-tool_ |
| M2 | No output template for structured output requirements | Templates eliminate format guessing and ensure consistent output across invocations. Especially important for reports, commit messages, API payloads, and any output consumed by downstream automation. | Provide a concrete template marked "ALWAYS use this exact structure" when consistency is critical; mark it as a sensible default when adaptation is acceptable |
| M3 | Missing "Gotchas" section for non-obvious traps | Naming inconsistencies (`user_id` in DB vs. `uid` in auth service), silent edge cases, and known footguns should be called out explicitly. Claude cannot infer these from context. | Add a "Gotchas" or "Common mistakes" section listing non-obvious traps by name with corrective guidance |
| M4 | Generic or meaningless file names in the skill directory (doc2.md, file1.md, utils.md) | Claude navigates the skill directory like a filesystem, using file names to decide which files to open. Opaque names reduce navigation accuracy and increase the chance Claude reads the wrong file or skips useful context. | Use descriptive names that signal content: _form_validation_rules.md_, _finance_metrics.md_ |
| M5 | Skill name does not start with the `df-` prefix | Project naming convention required for visual identification in the Claude Code console. Skills without this prefix cannot be distinguished from third-party skills at a glance. | _Bad:_ `analyze-data` · _Good:_ `df-analyze-data` |
| M6 | General technical explanations that Claude already knows | The context window is shared across all active skills, conversation history, and system prompt. Explaining what PDFs are or how HTTP works wastes tokens on every invocation without adding value. | Include only project-specific conventions and non-obvious edge cases Claude could not know from training |
| M7 | Magic constants in scripts without justification (Ousterhout's law) | Undocumented values (TIMEOUT = 47, RETRIES = 5) cannot be safely adjusted by maintainers and signal untested configuration. If the author can't justify the value, neither can Claude or future editors. | Add inline comments explaining the reasoning for each non-obvious numeric or string constant |
| M8 | No concrete examples for ambiguous output cases | When the skill involves tolerances, judgment calls, or format variants, more words fail where examples succeed. Two to four input/output pairs consistently outperform additional description for these cases. | Add concrete examples showing accepted vs. rejected cases for any ambiguous decision point |
